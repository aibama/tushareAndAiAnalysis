# Redis Stream 股票代码消费者

基于 Redis Stream 的分布式消息消费系统，用于异步处理股票代码数据。

## 概述

本模块实现了一个基于 Redis Stream 的股票代码消费者系统，采用消费者组模式实现多消费者并行处理，支持消息确认、pending 消息认领等高级特性。

## 处理流程

### 1. 消息生产（向 Stream 添加股票代码）

```java
@Autowired
private RedisStreamOperations redisStreamOperations;

// 添加股票代码到 Stream
Map<String, String> message = new HashMap<>();
message.put("stockCode", "0.002813");
redisStreamOperations.addMessage("stock-stream", message);
```

### 2. 消息消费（自动启动）

应用启动后，消费者自动从 Stream 中读取消息并处理：

```
1. 消费者阻塞等待消息 (block-ms: 5000ms)
   │
   ├─ 收到消息 → 处理 → 确认
   │     │
   │     ├─ 提取 stockCode
   │     ├─ 调用 StockDataProcessorService.processStockCode()
   │     ├─ 处理成功 → ACK 确认
   │     └─ 处理失败 → 不确认，保留在 pending
   │
   └─ 无消息 → 继续阻塞等待
```

### 3. Pending 消息认领

定时任务每 60 秒执行一次，处理长时间未确认的消息：

```
定时任务触发
  │
  ├─ 查询 pending 消息（空闲时间 > claimIdleTimeMs）
  ├─ 认领到当前消费者
  ├─ 重新处理
  └─ 确认
```

## 注意事项

### 1. Redis 版本要求

- 需要 Redis 5.0+ 以支持 Stream 数据结构

### 2. 消息确认机制

- **成功处理**：调用 `ackMessages()` 确认消息，消息从 pending 列表移除
- **处理失败**：不确认消息，消息保留在 pending 列表，可被认领重新处理
- **建议**：在业务处理中使用 try-catch，确保异常情况下不确认消息

### 3. 消费者组管理

- 消费者组创建是幂等的，多次创建不会报错
- 如果需要重置消费者组偏移量，需要手动使用 Redis 命令：
  ```bash
  XGROUP DESTROY stock-stream stock-group
  ```

### 4. Pending 消息认领

- 认领任务每 60 秒执行一次
- 只认领空闲时间超过 `claim-idle-time-ms`（默认 60 秒）的消息
- 认领者消费者名称格式：`{prefix}-{nodeId}-claimer`

### 5. 消费者线程数

- 默认 3 个线程，可根据服务器性能调整
- 线程数不宜过多，避免对下游服务造成压力
- 每个线程对应一个唯一的消费者名称

### 6. 消息格式

消息必须包含股票代码，支持以下字段名：

```json
{"stockCode": "0.002813"}
{"stock_code": "0.002813"}
{"code": "0.002813"}
{"0.002813"}  // 直接值
```

### 7. 多节点部署

- 每个节点应使用不同的 `node-id`
- 同一节点内的线程数由 `consumer-thread-count` 控制
- 消费者名称格式：`{consumer-name-prefix}-{nodeId}-thread{N}`

### 8. 监控与日志

- 关键日志级别：
  - `INFO`: 消费者启动、收到消息、处理完成
  - `WARN`: 消息格式异常、消费者已在运行
  - `ERROR`: 处理失败、连接异常

### 9. 故障恢复

- 消费者线程异常退出后会自动重启（因为是 daemon 线程）
- pending 消息会被定时任务认领并重新处理
- Redis 连接失败会有重试机制

### 10. 性能调优

| 参数 | 调整建议 |
|------|----------|
| `consumer-thread-count` | CPU 核心数的 2-3 倍 |
| `count` | 根据消息量调整，10-100 |
| `block-ms` | 根据实时性要求调整，1000-10000 |
| `claim-idle-time-ms` | 设置为业务处理超时时间的 2-3 倍 |

## 常见问题

**Q: 消息重复消费怎么办？**
A: 使用消息确认机制，确保处理成功后才 ACK。如果需要严格去重，可在业务层使用 Redis 分布式锁。

**Q: 消费者组偏移量如何重置？**
A: 使用 Redis 命令：`XGROUP SETKEY stock-stream stock-group 0`

**Q: 如何查看 pending 消息？**
A: 使用 Redis 命令：`XPENDING stock-stream stock-group`

**Q: 消费者启动失败怎么办？**
A: 检查：1) Redis 是否可用 2) 配置是否正确 3) Stream 键是否存在

## 去重与分布式锁

### 概述

本模块提供了基于 Redis 的严格去重和分布式锁功能，用于解决消息重复消费和并发处理问题。

### 核心组件

#### RedisDistributedLockService

**职责**：提供 Redis 分布式锁和去重功能

**位置**：[`RedisDistributedLockService.java`](src/main/java/com/example/service/emlevel2/RedisDistributedLockService.java:1)

**主要功能**：

| 功能 | 说明 |
|------|------|
| 分布式锁 | 基于 Redisson 的可重入锁 |
| 去重 | 基于 Redis Set 的严格去重 |
| 组合操作 | 带锁执行、去重+锁执行 |

#### 1. 自动集成（StockDataProcessorService）

`StockDataProcessorService` 已自动集成去重和分布式锁，处理股票代码时会自动：

1. 检查去重集合，如果已存在则跳过
2. 获取分布式锁，确保同一时刻只有一个节点处理
3. 执行处理逻辑
4. 释放锁

#### 2. 手动使用（其他业务服务）

其他包内的业务服务可以通过注入 `StockDataProcessorService` 或 `RedisDistributedLockService` 来使用去重和锁功能：

```java
@Autowired
private StockDataProcessorService stockDataProcessorService;

// 方式1：检查并添加去重（返回true表示需要处理）
boolean shouldProcess = stockDataProcessorService.checkAndAddDeduplication("0.002813");
if (shouldProcess) {
    // 执行处理逻辑
}

// 方式2：在分布式锁保护下执行
stockDataProcessorService.executeWithLock("my-lock-key", () -> {
    // 业务逻辑
});

// 方式3：在去重+锁保护下执行
stockDataProcessorService.executeWithDedupAndLock(
    "dedup-key",      // 去重key
    "0.002813",       // 去重值
    "lock-key",       // 锁key（可选，传null则不使用锁）
    () -> {
        // 业务逻辑
    }
);
```

#### 3. 直接使用 RedisDistributedLockService

```java
@Autowired
private RedisDistributedLockService lockService;

// 分布式锁使用
boolean locked = lockService.tryLock("order:123");
if (locked) {
    try {
        // 业务逻辑
    } finally {
        lockService.unlock("order:123");
    }
}

// 去重使用
boolean added = lockService.addToDedupSet("stock-code", "0.002813");
if (added) {
    // 执行处理
} else {
    // 已存在，跳过
}

// 组合操作
lockService.executeWithDedupAndLock("stock", "0.002813", "lock:002813", () -> {
    // 处理逻辑
});
```

### 去重原理

1. **基于 Redis Set**：使用 Redis Set 存储已处理的值，Set 的 `add` 操作是原子的
2. **严格去重**：只有首次添加返回 true，重复添加返回 false
3. **自动清理**：可通过配置设置过期时间，或手动调用 `clearDedupSet` 清理

### 分布式锁原理

1. **基于 Redisson**：使用 Redisson 的 `RLock` 实现
2. **可重入**：同一线程可以多次获取同一把锁
3. **自动释放**：支持设置锁的过期时间，防止死锁
4. **公平锁**：支持公平锁模式（可选）

### 注意事项

1. **锁超时**：合理设置锁的过期时间，避免处理时间过长导致锁自动释放
2. **去重清理**：定期清理过期的去重记录，避免内存占用
3. **异常处理**：确保在异常情况下也能正确释放锁和移除去重标记
4. **多节点部署**：分布式锁和去重在多节点环境下都能正常工作
